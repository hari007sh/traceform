# Route (Gateway)

Route is Traceform's gateway module. It provides an OpenAI-compatible proxy server (port 8090) that sits between your application and LLM providers. It handles model routing, provider failover, semantic caching, and request logging -- all with less than 5ms overhead.

## Overview

The gateway proxy accepts standard OpenAI API format and routes requests to any configured provider:

- **OpenAI** -- GPT-4o, GPT-4, GPT-3.5
- **Anthropic** -- Claude 3.5 Sonnet, Claude 3 Opus, Claude 3 Haiku
- **Google** -- Gemini Pro, Gemini Ultra
- **Together** -- Open-source models (Llama, Mistral, etc.)
- **Groq** -- Fast inference for open-source models
- **Mistral** -- Mistral Large, Medium, Small

## How It Works

### Request Pipeline

```
Client Request (OpenAI format)
    |
    v
1. Authenticate (X-Traceform-Org-ID header)
    |
    v
2. Check circuit breaker state for target provider
    |-- OPEN --> Try next provider or return 503
    |
    v (CLOSED or HALF-OPEN)
3. Check singleflight cache (deduplicate concurrent identical requests)
    |
    v
4. Check semantic cache (Redis fast path, PostgreSQL slow path)
    |-- Cache HIT --> Return cached response (X-Traceform-Cache-Hit: true)
    |
    v (Cache MISS)
5. Match routing rules (glob pattern on model name)
    |
    v
6. Select provider via strategy (priority / round_robin / cost)
    |
    v
7. Forward request to provider (streaming or non-streaming)
    |-- Client disconnects --> Cancel upstream request (context cancellation)
    |
    v
8. Record cost event with accurate token counts
    |
    v
9. Store response in cache (async)
    |
    v
10. Log request via NATS (async)
    |
    v
Return response (X-Traceform-Provider / X-Traceform-Model headers)
```

### Circuit Breakers

Each provider has an independent circuit breaker that tracks consecutive failures:

| State | Behavior |
|-------|----------|
| **Closed** | Requests flow normally. Failure counter increments on errors. |
| **Open** | All requests are rejected immediately. Transitions to half-open after cooldown. |
| **Half-open** | A single probe request is allowed. Success closes the circuit; failure reopens it. |

Configuration:
- **Failure threshold**: Number of consecutive failures before the circuit opens (default: 5)
- **Cooldown period**: Duration the circuit stays open before transitioning to half-open (default: 30 seconds)

When a circuit is open, the gateway automatically tries the next provider in the fallback chain or returns a `503 Service Unavailable`.

### Singleflight Cache

The singleflight cache deduplicates concurrent identical requests. If multiple clients send the same request (same model, messages, temperature, tools) at the same time, only one request hits the upstream provider. All other clients receive the same response.

This is separate from the semantic cache -- singleflight operates on in-flight requests, while the semantic cache operates on completed responses.

### Streaming with Context Cancellation

When a client disconnects mid-stream (e.g., user navigates away), the gateway properly cancels the upstream request to the provider:

1. Client SSE connection drops
2. Go context is cancelled
3. Upstream HTTP request is aborted
4. No further tokens are consumed or billed

This prevents wasted API calls and costs when users abandon streaming responses.

### Cost Recording Fix

The gateway accurately records token usage and cost for both streaming and non-streaming responses:

- **Non-streaming**: Token counts are extracted from the `usage` field in the response
- **Streaming**: Token counts are accumulated from `stream_options: { include_usage: true }` or estimated from chunk content length

### Routing Rules

Routing rules match the requested model name using glob patterns and direct the request to a specific provider and target model.

| Field | Description |
|-------|-------------|
| `model_pattern` | Glob pattern to match against the requested model (e.g., `gpt-4*`, `claude-*`, `*`) |
| `provider_id` | ID of the configured provider to route to |
| `target_model` | The actual model name sent to the provider |
| `strategy` | How to select among multiple matching routes |
| `priority` | Priority when using the `priority` strategy (higher wins) |
| `weight` | Weight when using the `cost` strategy (lower wins) |

### Routing Strategies

When multiple routes match a model request:

| Strategy | Selection Logic |
|----------|----------------|
| `priority` (default) | Selects the route with the highest `priority` value |
| `round_robin` | Cycles through matching routes sequentially |
| `cost` | Selects the route with the lowest `weight` value |

### Semantic Caching

The gateway uses SHA-256 exact-match caching. The cache key is computed from a normalized representation of:

- Organization ID
- Model name
- Messages array
- Temperature
- Tools

Lookups use a two-tier strategy:

1. **Redis fast path**: In-memory lookup with configurable TTL (default: 1 hour)
2. **PostgreSQL slow path**: Durable fallback that handles Redis restarts

Cache can be disabled per-request with the `X-Traceform-Cache: false` header.

### Fallback Chains

Fallback chains define ordered lists of provider/model pairs. When the primary provider fails (or its circuit breaker is open), the gateway automatically tries the next entry in the chain.

```json
{
  "name": "GPT-4 fallback chain",
  "model_pattern": "gpt-4*",
  "chain": [
    { "provider_id": "prov_openai", "model": "gpt-4o" },
    { "provider_id": "prov_anthropic", "model": "claude-3-5-sonnet-20241022" },
    { "provider_id": "prov_google", "model": "gemini-pro" }
  ],
  "enabled": true
}
```

### Provider API Key Security

Provider API keys are encrypted with AES-256-GCM before storage. The `ENCRYPTION_KEY` environment variable (32-byte hex string, 64 characters) is used for encryption and decryption at runtime. Keys are never stored in plaintext and never appear in API responses.

## API Reference

### Chat Completions (Gateway Proxy)

```bash
curl http://localhost:8090/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "X-Traceform-Org-ID: org_abc123" \
  -d '{
    "model": "gpt-4o",
    "messages": [
      {"role": "user", "content": "Hello, world!"}
    ]
  }'
```

The response follows the standard OpenAI chat completion format. Additional headers:

| Header | Description |
|--------|-------------|
| `X-Traceform-Provider` | The provider that handled the request |
| `X-Traceform-Model` | The actual model used |
| `X-Traceform-Cache-Hit` | `true` if served from cache, `false` otherwise |
| `X-Traceform-Circuit-State` | Circuit breaker state for the provider |

Streaming is supported -- set `"stream": true` in the request body.

### Embeddings (Gateway Proxy)

```bash
curl http://localhost:8090/v1/embeddings \
  -H "Content-Type: application/json" \
  -H "X-Traceform-Org-ID: org_abc123" \
  -d '{
    "model": "text-embedding-3-small",
    "input": "The quick brown fox"
  }'
```

### Add a Provider

```bash
curl -X POST http://localhost:8080/v1/gateway/providers \
  -H "Authorization: Bearer tf_sk_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "openai",
    "display_name": "OpenAI",
    "api_key": "sk-your-openai-key",
    "base_url": "https://api.openai.com/v1",
    "is_enabled": true,
    "config": {}
  }'
```

The `api_key` field is accepted on create/update but never returned in responses.

### Create a Route

```bash
curl -X POST http://localhost:8080/v1/gateway/routes \
  -H "Authorization: Bearer tf_sk_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "GPT-4o via OpenAI",
    "model_pattern": "gpt-4o*",
    "strategy": "priority",
    "provider_id": "prov_abc123",
    "target_model": "gpt-4o",
    "priority": 100,
    "enabled": true
  }'
```

### Create a Fallback Chain

```bash
curl -X POST http://localhost:8080/v1/gateway/fallbacks \
  -H "Authorization: Bearer tf_sk_your_key" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "GPT-4 failover",
    "model_pattern": "gpt-4*",
    "chain": [
      { "provider_id": "prov_openai", "model": "gpt-4o" },
      { "provider_id": "prov_anthropic", "model": "claude-3-5-sonnet-20241022" }
    ],
    "enabled": true
  }'
```

### Cache Management

```
GET /v1/gateway/cache/stats   -- Cache statistics
POST /v1/gateway/cache/purge  -- Purge the semantic cache
```

## Dashboard Guide

### Route Overview (`/dashboard/route`)

Displays:
- **Metric cards**: Total requests, cache hit rate, average latency, active providers (with circuit breaker states).
- **Requests over time**: Area chart of gateway request volume (uses the global time range picker).
- **Provider distribution**: Pie chart showing traffic split across providers.
- **Latency distribution**: Histogram of response times.
- **Circuit breaker status**: Visual indicator for each provider (closed/open/half-open).
- **Recent requests table**: Latest gateway requests with model, provider, latency, cache hit, and status.

### Provider Management (`/dashboard/route/providers`)

CRUD interface for managing providers. Add, edit, enable/disable, and delete providers. API keys are masked in the UI and can only be set (not read back). Circuit breaker states are displayed next to each provider.
